# Theme Migration 要件定義 v0.2「テーマごと運ぶ」

版: 0.2（案）／対象: BLOCK THEME MIGRATION 0.5.6 の次の改修
前版: `editor-import-requirements.md`（v0.1、エディター方式の取り込み）は、本書に置き換える。
v0.1 のうち、検証・サイト固有値の扱い・エディター内の変換は、範囲を絞って本書に引き継ぐ。

---

## 1. 目的

開発サイトのブロックテーマを、**デザインごと**別のサイトへ運ぶ。

- 移植元のデータベース（テンプレート、パーツ、同期パターン、グローバルスタイル）と、テーマフォルダ
  （`theme.json`、`styles/`、`patterns/`、`style.css`）から、**新しいテーマフォルダ（ZIP）**を作る。
- 移植先では、そのサイトが**すでに持っている投稿タイプ・タクソノミー・カスタムフィールドに紐づけて**取り込む。
- 移植先のサイトの構造（メニュー、ページ、表示設定、中身）は、**尊重して触らない**。

デザインの変更（再スキン）は、利用者が移植先で任意に行うもので、このツールの範囲外とする。

---

## 2. 決定事項

| # | 決定 |
|---|---|
| D1 | 基本のモードは、テーマごと運ぶこと。`theme.json` とバリエーションが一緒に動くので、色・余白・幅・フォントの写像はしない |
| D2 | 再スキン（別のテーマの値への写像）は、範囲外。利用者が移植先で行う |
| D3 | データモデル（投稿タイプ、タクソノミー、カスタムフィールド）は、**宣言だけ**を運ぶ。移植先で**作らない**。既存のものへの紐づけだけを行う |
| D4 | `front-page` と `404` のテンプレートは、テーマの一部として運ぶ |
| D5 | **表示設定（フロントページの表示、投稿ページ）は、移植先に反映しない** |
| D6 | **ナビゲーションメニューの紐づけは、運ばない。** ナビゲーションブロックの参照（`ref`）は外し、利用者が移植先で選ぶ |
| D7 | **内部リンク（移植元のページへのリンク）は、外す**（空にする）。**外部サイトへのリンクは残す** |
| D8 | 中身（投稿、リソース、枠、メディア、ユーザー）は、運ばない |
| D9 | Theme Migration の最低バージョンは、**WordPress 6.6 以上**（出力が `theme.json` version 3 のテーマになるため）。ブロックのプラグイン群は 6.4 のまま |
| D10 | SCF の定義の取り出しは、**読み取り専用**でよい |
| D11 | 書き出しをブラウザー内の処理にして時間がかかる場合は、**処理中の表示**を出す（特別な最適化は、後回し） |
| D12 | ブロックの保存形式の単一化は、**本改修とは別に、別途検討する** |

D6・D7 により、現行のリンク対応表（ページの対応付け）と、メニューの扱いは不要になる（§12）。

## 3. 現状（コードで確認したこと）

| 項目 | 確認結果 |
|---|---|
| WordPress 標準のエクスポート | `wp_generate_block_templates_export_file()` は、**テーマフォルダ全体をコピー**する（`wp_is_theme_directory_ignored()` の除外のみ）。そのため `styles/`（バリエーション）、`patterns/`、`style.css` は、すでに含まれる |
| 置き換わるもの | `templates/`、`parts/`、`theme.json` だけが、DB の変更を反映した内容になる |
| 現行プラグインの追加分 | 同期パターン（`core/block`）をテーマのパターンに変換、`theme.json` にパーツ・割り当て情報を追加、マニフェスト v4 を作成 |
| 現行の取り込み | PHP が、配列と文字列を書き換え、テンプレートを DB に保存（管理対象として識別） |
| データモデル | 開発サイトも sazanka も、Secure Custom Fields が、定義を DB の投稿として持つ（`acf-field-group`、`acf-field`、`acf-post-type`、`acf-taxonomy`）。宣言として書き出せる見込み（取り出す関数の動作は未確認） |

## 4. 範囲

### 4.1 運ぶもの

- テーマフォルダ全体（`theme.json`、`styles/`、`patterns/`、`style.css`、`screenshot.png`、`assets/` など）
- DB の変更を反映したテンプレート、テンプレートパーツ、グローバルスタイル
- 同期パターン（テーマのパターンへ変換）
- データモデルの**宣言**（§6.2）と、使用箇所の索引
- 依存の宣言（プラグイン、ブロック、最低バージョン）

### 4.2 外すもの（除去して、レポートに載せる）

| 対象 | 処置 |
|---|---|
| 内部リンク（移植元のページ） | 空にする。外部リンクは残す |
| ナビゲーションの参照（`core/navigation` の `ref`） | 外す |
| メールアドレス（送信先など） | 空にする。フッター文中は `[master_name]` / `[master_mail]` に置換 |
| 移植元のメディア（`wp-content/uploads/`） | 空のブロックにする。プラグイン同梱のアセットは、ルート相対にして残す |
| 投稿 ID などの ID 参照 | 既定値に戻す |
| 保存済みプレビューの文字（動的に置き換わるタイトルの見本など） | 空にする |

### 4.3 運ばないもの

- 投稿、固定ページ、リソース、枠、メディア、ユーザー（D8）
- 表示設定、メニュー、ウィジェット、プラグインの設定値（D5、D6）
- データモデルの**実体**（作らない、D3）

## 5. 全体フロー

```
[移植元サイト]                                        [移植先サイト]
 ① 収集   DB＋テーマフォルダ                           ⑥ テーマとして導入（標準の ZIP インストール）
 ② 宣言   データモデル・使用箇所・依存                  ⑦ 依存の検査
 ③ 除去   内部リンク・メニュー参照・メール等             ⑧ 紐づけ  投稿タイプ／タクソノミー／フィールド
 ④ 検証   全ブロックが有効か                           ⑨ 検証    全ブロックが有効か
 ⑤ 出力   新しいテーマ ZIP ＋ マニフェスト v5           ⑩ 適用    DB に上書き（管理対象・取り消し可）
                                                        ⑪ レポート 要設定の一覧
```

- 出力される ZIP は、**普通のテーマ ZIP**である。プラグインが無くても、標準の方法で導入できる。
  取り込みのウィザード（⑦〜⑪）は、そのうえでの任意の補助である。
- ③の除去は、書き出す前に行う。ZIP にメールアドレスや移植元のページへのリンクが残らないようにするため。

## 6. 機能要件

### 6.1 書き出し（移植元）

**EX-1 テーマフォルダ全体の出力。** 標準のエクスポートを土台にし、現行の拡張（同期パターンの変換、`templateParts` の登録、割り当て情報）を維持する。
**EX-2 同梱の確認。** `styles/`、`patterns/`、`style.css`、スクリーンショットが、ZIP に含まれていることを検査する。含まれなければ報告する。
**EX-3 除去（§4.2）。** 書き出す前に、テンプレート、パーツ、パターンの全ブロックに対して適用する。処置はブロック名ごとの規則に従う（§7）。
**EX-4 除去の方式。** 段階的に、エディター内の方式へ移す（§10）。初期は、除去の**検出のみ**を行い、レポートで一覧にする。
**EX-5 検証。** 書き出す前に全ブロックの有効性を確認する。無効があれば、原因（期待値と実際の値）を示し、書き出しを止めるか、無効の項目を除くかを選ばせる。
**EX-6 データモデルの宣言（§6.2）をマニフェストに入れる。**
**EX-7 依存の宣言。** 使われているブロックから、必要なプラグイン、ブロック、最低バージョンを導く。
**EX-8 中身を含めない。** 投稿、メディア、ユーザー、設定値は出力しない（D8）。

### 6.2 データモデルの宣言

マニフェスト v5 に、次を入れる。**定義の書き出しは、情報としてのみ**で、取り込み時に作成には使わない（D3）。

| 項目 | 内容 |
|---|---|
| `postTypes` | スラッグ、ラベル、サポート、関連するタクソノミー、使われているテンプレート |
| `taxonomies` | スラッグ、ラベル、対象の投稿タイプ |
| `fieldGroups` | グループ名、対象の投稿タイプ、フィールド（名前、種類、選択肢） |
| `usage` | どのテンプレート／パーツ／パターンの、どのブロックの、どの属性が、どの投稿タイプ・タクソノミー・フィールドを参照しているか |
| `postMeta` | `meta_` で始まる参照（連携プラグインなどが保存する投稿メタ）。キーと、登録されたメタキーか。カスタムフィールド（SCF／ACF）とは区別する（M2 の実装で、実データから判明） |

- 取得元: SCF の定義（`acf-*` 投稿）、および `get_post_types()`、`get_taxonomies()`。
- `usage` は、ブロックの属性から抽出する（§7 の規則を使う）。

### 6.3 取り込み（移植先）

**IM-1 導入。** パッケージは、標準のテーマ ZIP として導入する。取り込みウィザードは、導入済みのテーマ（有効でも、有効化前でもよい）のマニフェストを読む。
**IM-2 依存の検査。** マニフェストの `requires` を、プラグインの有効化、ブロックの登録、最低バージョンについて検査する。不足は示すだけで、自動の導入・有効化はしない。
**IM-3 紐づけ（§6.4）。**
**IM-4 適用。** 紐づけの結果を、テンプレート、パーツ、パターンへ反映し、DB へ保存する。保存は、現行の「管理対象」の仕組み（識別メタ、再実行で重複しない）を維持する。
**IM-5 取り消し。** 適用前の内容を退避し、取り込み単位で復元できる。管理対象の一覧と、テーマ原本へ戻す機能（現行）を維持する。
**IM-6 ドライラン。** 既定は、保存しない実行。差分（変換された属性のパスと前後の値）と、レポートを確認してから適用する。
**IM-7 レポート。** 「要設定」の一覧を出す（§6.5）。
**IM-8 範囲の遵守。** 表示設定、メニュー、ページ、中身には、一切書き込まない（D5、D6、D8）。

### 6.4 紐づけ

**BD-1 投稿タイプ。** 移植元の投稿タイプのアーカイブ・個別テンプレート（例: `archive-product`、`single-product`）を、移植先で登録済みの投稿タイプへ紐づける。
- 候補は、移植先で公開されている投稿タイプ。名前・スラッグの近さで**自動提案**し、利用者が確認する。
- 紐づけると、テンプレート名（`archive-works` など）と、ブロックが持つ投稿タイプの参照（`selectedSlug` など）が、**同時に**置き換わる。
- 「紐づけない」を選べる（そのテンプレートは取り込まない）。

**BD-2 タクソノミー。** 投稿タイプと同様に、候補を提案して紐づける。

**BD-3 カスタムフィールド。** ブロックが参照するフィールド名（例: `acf_gallery`）を、移植先のフィールド名へ紐づける。
- 参照を一覧にして、対応表を作る。移植先に対応するフィールドが無ければ、「無視する（参照を空にする）」を選ぶ。**作らない**（D3）。
- 候補は、紐づけ先の投稿タイプに属するフィールドに絞る。

**BD-4 固定ページ。** 固定ページ用のテンプレートは、テーマの `customTemplates` として運ぶ。利用者が、移植先のページ編集画面で選ぶ。
現行の「テンプレートを特定のページに割り当てる」機能は、**任意の補助**として残す（リンクの変換はしない）。

**BD-5 置き換え規則はブロック名ごと。** 同じ属性名でも、意味がブロックで違う（`selectedSlug` は、`design-button` では固定ページ、query-blocks では投稿タイプ）。
そのため、規則は「ブロック名 × 属性パス × 種類（投稿タイプ／タクソノミー／フィールド／ページ）」で定義する（§7）。現行の「`selectedSlug` を無条件にページへ書き換える」不具合は、これで解消する。

**BD-6 保存の形。** 紐づけの結果（対応表）を、有効テーマごとに保存し、再実行・再訪問で復元する（現行のマッピング保存を継続）。

### 6.5 レポート

取り込み・書き出しのたびに、次を出す。画面で見られ、JSON でダウンロードできる。

| 区分 | 内容 |
|---|---|
| 要設定 | 外したリンク（テンプレート、ブロック、ラベル）、外したメニューの参照、紐づけが未完了の参照 |
| 紐づけ | 投稿タイプ、タクソノミー、フィールドの対応表と、置き換えた箇所の数 |
| 検証 | 無効なブロックの一覧と原因 |
| 除去 | 外したもの（メール、メディア、ID）の件数 |
| 依存 | 不足しているプラグイン・ブロック |

## 7. ブロック規則（属性の意味の宣言）

> 調査結果（実データでの洗い出し）は `link-attribute-survey.md` にある。本節は、その結果を反映している。

置き換え・除去の規則を、**ブロック名ごとのデータ**として持つ。ブロックを提供するプラグインが、フィルターで追加できる
（現行の `itmar_btm_prepare_blocks` の発展）。

```json
{
  "itmar/design-button": [
    { "path": "selectedSlug",     "kind": "page" },
    { "path": "selectedPageUrl",  "kind": "page-url" }
  ],
  "itmar/pickup-posts": [
    { "path": "selectedSlug",     "kind": "post-type" },
    { "path": "selectedTaxonomy", "kind": "taxonomy" }
  ],
  "core/navigation": [
    { "path": "ref",              "kind": "navigation" }
  ]
}
```

| kind | 書き出し時 | 取り込み時 |
|---|---|---|
| `page`／`page-url` | 内部リンクなら空にする。外部 URL は残す | （何もしない） |
| `navigation` | 外す | （何もしない） |
| `post-type` | 使用箇所として宣言 | 紐づけ先へ置換 |
| `taxonomy` | 使用箇所として宣言 | 紐づけ先へ置換 |
| `field` | 使用箇所として宣言 | 紐づけ先へ置換、または空にする |

- 内部リンクの判定: 移植元のホーム URL で始まる、または `[home_url]` で始まる、または相対パス。それ以外は外部。
- **`linkKind` による条件。** `design-button`・`design-title` の `selectedSlug` は、`linkKind` が `fixed` なら固定ページの slug（外す）、
  `archive`／`single` なら投稿タイプの slug（紐づけの対象）である。規則は `when: { "linkKind": … }` の条件を持てること。
  特殊値 `__home__` も、リンクとして外す。
- **埋め込みブロックの再帰。** `pickup-posts`・`product-block`・`cart-block` の `blocksAttributesArray`、`post-pagenation`・`post-filter`・`post-crumbs` の
  `…Attributes`、`markdown-block` の `element_style_obj` は、別のブロックの属性を内側に持つ。`embedded-blocks`／`embedded-attributes` の規則で、
  埋め込まれたブロック名の規則を再帰して適用する。
- **本文の `<a href>`。** コアの本文（段落、リスト、見出し）のリンクも対象。内部なら `href` を外し、文字は残す。外部は残す。
- **保存された投稿データ。** `pickup-posts` の `posts`（取得済みの投稿の一覧）は、移植元の投稿の内容なので空にする（D8）。
- **メディア。** `media` のオブジェクトと `core/image` の `url` は、メディアの除去（§4.2）で扱う。リンクとは別に処理する。
- **`.local` ホスト。** 内部リンクの判定では、移植元のホームだけでなく、**`.local` で終わるホストをすべてサイト固有の URL として扱う**
  （過去の開発サイトの URL が混在していたため）。
- **規則の置き場所と種。** 初期の規則データは `link-attribute-survey.md` §5 にある。
- ブロック規則が無いブロックの属性には、触らない（変更しないことを原則とする）。
- 規則の網羅性は、スキャン（§8）で補う。既知のキー（`selectedSlug`、`redirectPath`、`url` など）が、規則の無いブロックに現れたら警告する。

## 8. 検証とスキャン

**VL-1 有効性の検証。** 書き出し前（EX-5）と、取り込み後（IM-4 の前）に、全ブロックの `isValid` を確認する。
**VL-2 安定性の確認。** 書き出した本文を解析し直し、再度書き出して一致すること（浮動小数点の表記を除く）。
**VL-3 サイト固有値のスキャン。** 次を検出して一覧にする。

| 種類 | 検出 |
|---|---|
| メールアドレス | `@` を含む文字列 |
| メディア | `wp-content/uploads/` を含む URL、`core/image` の `id` |
| ID 参照 | 投稿 ID（`wp:block` の `ref` など） |
| 絶対 URL | 移植元のホーム URL、`.local` |
| 未登録のブロック | 移植元に登録されていないブロック名 |

**VL-4 単体の検証モード。** 書き出し・取り込みを行わず、既存のテンプレート・パーツの有効性だけを数える（開発サイトでの確認用）。

```json
{
  "schemaVersion": 5,
  "theme": { "slug": "develope-theme", "name": "…" },
  "requires": {
    "plugins": [{ "slug": "block-collections", "minVersion": "…" }],
    "blocks":  ["itmar/design-group", "itmar/reservation-block"]
  },
  "dataModel": {
    "postTypes":  [{ "slug": "product", "labels": {…}, "taxonomies": ["product_cat"] }],
    "taxonomies": [{ "slug": "product_cat", "postTypes": ["product"] }],
    "fieldGroups":[{ "title": "…", "postTypes": ["product"], "fields": [{ "name": "gallery", "type": "gallery" }] }],
    "usage": [
      { "item": "templates/archive-product.html", "block": "itmar/pickup-posts",
        "path": "selectedSlug", "kind": "post-type", "value": "product" }

  "templates": [ … ],
  "templateParts": [ … ],
  "patterns": [ … ],
  "report": { "removed": {…}, "needsSetup": [ … ] }
}
```

- v4 のマニフェストも読めること（後方互換）。
- `homeUrl` は、内部リンクの判定のために、引き続き持つ。

## 10. 実装方式

**除去・置換の方式は、段階的に変える。**

| 段階 | 方式 |
|---|---|
| 初期 | 検出と報告のみ（本文は書き換えない）。現行の PHP の処理は維持 |
| 本格 | エディター内の方式。`parse` → 属性だけを変換 → `createBlock` → `serialize`（= `save()`）。検証もここで行う |

エディター方式にする理由: PHP は `save()` を実行できないため、コメント・`data-attributes`・インライン style の三重の表現を、手で揃えるしかない。
実際の移植（2026-10-04）で、既定値のキーの書き足し漏れによる大量の無効、インライン style の取りこぼし、`data-attributes` の所在（内側の `<div>`）の見落としが発生した。エディターの `save()` を通せば、これらは起きない。

- 書き出し側も、**ブラウザー内の処理**にする: サーバーが生の内容を渡す → エディターが除去・検証 → 清書した内容をサーバーへ返す → サーバーが ZIP を組む。
- 焼き直し（影、ラベル幅の再計算）は、不要になる見込み（`theme.json` が同じなので、値が同じになる）。必要なら、検証と同じ仕組みで行う。
- 参考: 保存された JSON の往復（コメント・`data-attributes`）は、全ブロックでバイト一致することを確認済み。

## 13. 受け入れ基準

**AC-1（運ぶ）** 開発サイトのテーマを書き出し、別のサイトに導入すると、同じデザインで表示される（テーマの `styles/`、`patterns/`、`style.css` も含む）。
**AC-2（外す）** 書き出した ZIP に、メールアドレス、`wp-content/uploads/` の URL、移植元のページへのリンク、ナビゲーションの参照が残らない。外部リンクは残る。
**AC-3（紐づけ）** 移植元の `archive-product` / `single-product` を、移植先の登録済みの投稿タイプ（例: `works`）へ紐づけて取り込める。テンプレート名と、ブロックの投稿タイプの参照が、同時に置き換わる。
**AC-4（フィールド）** ブロックが参照するカスタムフィールドを、移植先のフィールドへ紐づけられる。対応が無いものは、参照が空になる。**フィールドは作られない**。
**AC-5（範囲）** 取り込みで、表示設定、メニュー、ページ、中身が変更されない。
**AC-6（検証）** 書き出し・取り込みのたびに、全ブロックが有効であることが確認される。無効があれば、原因が報告され、そのまま適用されない。
**AC-7（取り消し）** 適用を、取り込み単位で、一括で元に戻せる。
**AC-8（依存）** 必要なプラグイン・ブロックが無いとき、取り込み前に不足が示される。
**AC-9（レポート）** 「要設定」の一覧（外したリンク、メニュー、未完了の紐づけ）が出る。
**AC-10（回帰）** 既存の移植（作品アーカイブ、ログイン、会員登録、予約管理）が、同じ結果になる。
