# Theme Migration：エディター方式の取り込み 要件定義

版: 0.1（案）／対象: BLOCK THEME MIGRATION 0.5.6 の次の大改修

この文書は、取り込み（移植先での適用）を「サーバー側の文字列・配列の書き換え」から
「ブロックエディターで解析し、属性を変換し、`save()` で書き出す」方式に変えるための要件を定める。
実装はこの文書への合意のあとに始める。

---

## 1. 背景と目的

### 1.1 現状の構造

現在の取り込みは、すべてサーバー側（PHP）で行っている。

- 配布 ZIP（`wp_generate_block_templates_export_file()` ＋ `block-theme-migration.json`）を作る
- 移植先で、`parse_blocks()` した配列や、保存済み HTML の文字列を書き換える
  （リンク置換 `replace_links_in_json_value()`、HTML 内の JSON の書き換え、`stable_serialize_blocks()`、
  `restore_registered_object_attribute_shapes()` など）
- 書き換えたものを、そのまま `wp_template` / `wp_template_part` / `wp_block` に保存する

### 1.2 根本の問題

PHP は `save()` を実行できない。そのため、静的に保存される itmar ブロックは、
**同じ値がブロックコメント・`data-attributes`・インライン style の3か所に持たれ、PHP はそれらを
互いに矛盾しないよう手で揃えるしかない。**

README に並ぶ個別の対策（`data-selected_page` の同時変換、HTML 内 JSON の同時変換、浮動小数点の安定化、
空オブジェクトの形の保持、`dateSpan` の復元など）は、すべてこの構造の症状である。
2026-10-04 の予約管理ページの移植で、次の問題が実際に出た。

| 問題 | 内容 |
|---|---|
| 既定値のキーの食い違い | 既定値のままの属性はコメントに無い。`data-attributes` だけを書き換えると、エディターは既定値に戻して食い違い、19ブロックが「無効」になった |
| インライン style の取りこぼし | `--itmar-hamburger-bar:#ffffff` のような CSS 変数が、属性の外にも出る |
| `data-attributes` の所在 | design-group は内側の `<div>` に付く。直後の1タグだけを見ると取りこぼす |
| 環境で変わる値 | 影（背景色から計算）、ラベル幅（フォントで実測）は、移植先のエディターで計算し直される。ファイルのままでは移植元の値が残る |
| 検証の不在 | ブロックの有効性は JS でしか判定できず、移植後に毎回ログインして開いて確かめた |
| 値の写像 | 余白、幅、フォント、色のスロット名が環境で違う。サイト固有の値（ID、メール、見本の文字）も混ざる |

### 1.3 目的

**取り込みを、移植先のブロックエディター上で実行する。** 実際に登録されたブロックの `parse` / `createBlock` /
`serialize`（= `save()`）を使うことで、次を移植先の環境が自動で正しく行う。

1. 既定値の補完と、コメント・`data-attributes`・インライン style の整合
2. 環境から計算される値（影、ラベル幅など）の再計算
3. 有効性の判定

人が書く規則は、**属性（JavaScript のオブジェクト）に対する変換**だけになる。文字列の書き換えは行わない。

## 2. 基本原則

| # | 原則 |
|---|---|
| P1 | 変換は属性オブジェクトに対して行う。文字列・正規表現による本文の書き換えをしない |
| P2 | 書き出しは必ず `save()` を通す（`wp.blocks.serialize`）。サーバー側で本文を組み立てない |
| P3 | 取り込みは移植先のエディターで行う。登録されていないブロックがあれば、変換せず報告する |
| P4 | 適用の前に、検証（`isValid`）が全ブロックで通ることを確認する。通らなければ適用しない |
| P5 | ドライラン（保存しない実行）を標準にする。結果は差分とレポートで確認できる |
| P6 | 移植元のメディア、実メールアドレス、ID 参照を、移植先へ持ち込まない |
| P7 | 失敗しても元に戻せる。適用前の状態を保持する |
| P8 | 変換規則はデータ（JSON）で表し、コードに埋め込まない |

---

## 3. 用語

- **パッケージ**: Distribution Export が作る配布物（テーマ ZIP ＋ マニフェスト）
- **取り込み**: 移植先で、パッケージの内容を選び、変換して、適用すること
- **変換規則**: 属性に対する書き換えの定義（§6.4）
- **焼き直し（bake）**: ブロックを実際にマウントし、環境依存の値を計算し直して書き出すこと
- **管理対象**: 取り込みツールが作った `wp_template` / `wp_template_part` / `wp_block`（既存の仕組みを継続）

---

## 4. 全体フロー

```
 [パッケージ読込]──▶[選択]──▶[変換規則の設定]──▶[スキャン]──▶[変換＋検証（ドライラン）]
        │              │            │                │                    │
   manifest v2     個別選択      写像の候補        サイト固有値         差分・無効の一覧
   依存の検査      依存の連動     自動提案          の検出               （保存しない）
                                                                          │
                                                          [焼き直し]──▶[適用]──▶[レポート]
                                                           マウント         保存＋退避      ログ
                                                           再計算           ロールバック可
```

エディター内での処理の流れ（1項目あたり）:

```
 本文(HTML/コメント) ──parse──▶ ブロックツリー
        ──変換規則を適用（属性のみ）──▶ ブロックツリー'
        ──validate（isValid）──▶ 無効があれば中止して報告
        ──マウント（BlockEditorProvider）──▶ 環境依存の値を再計算
        ──serialize（save）──▶ 本文'
        ──再度 parse して一致を確認（安定性）──▶ 保存
```

## 5. 範囲

### 5.1 範囲内

- 移植先での取り込み処理（変換・検証・焼き直し・保存）をエディター方式に置き換える
- 変換規則の定義、UI、保存
- サイト固有値の検出と除去
- 依存の検査（マニフェスト v2）
- ドライラン、レポート、ロールバック

### 5.2 範囲外（今回は扱わない）

- Distribution Export 側（開発サイトでの ZIP 作成）の作り直し。ただしマニフェスト v2 の項目追加は含む
- ブロック自体の保存形式の単一化（`data-attributes` の廃止）。別の大改修として検討する
- 移植先のスタイルバリエーションの自動生成
- 有料配布のライセンス管理

## 6. 機能要件

### FR-1 パッケージとマニフェスト v2

**FR-1.1** 既存のマニフェスト（`block-theme-migration.json`）を読めること（後方互換）。
**FR-1.2** v2 では次を追加する。

| 項目 | 内容 |
|---|---|
| `schema` | `2` |
| `tokens` | パッケージが前提にする役割（色・フォント・余白・幅・見出しサイズ）の一覧と、移植元での実体 |
| `requires.plugins` | 必要なプラグインとブロック（例: `itmar/reservation-block`）と最低バージョン |
| `requires.postTypes` | 必要な投稿タイプ（SCF の定義の書き出しを添付できる） |
| `requires.options` | 設定すべきオプション（例: 予約のリソースの投稿タイプ） |
| `pages` | 作るべきページ（slug、タイトル、割り当てるテンプレート） |
| `items` | 取り込める単位（テンプレート、パーツ、パターン）と、相互の参照 |
| `siteSpecific` | 移植元のサイト固有値の宣言（メール、ID、見本の文字の場所） |

**FR-1.3** `items` の各項目は、本文を **ブロックのシリアライズ済み HTML** として持つ（現状どおり）。
解析はエディターで行うので、JSON 化したブロックツリーを別に持つ必要はない。

### FR-2 取り込みの単位と選択

**FR-2.1** テンプレート、パーツ、パターンを、**個別に選べる**こと（現状は割り当て可能なテンプレートのみ）。
**FR-2.2** 選んだ項目が参照する他の項目（例: `header-menu` → `menu-body`）を検出し、**連動して選択**する。外すと警告する。
**FR-2.3** 取り込み時に、パーツ・テンプレートの slug を**付け替えられる**こと（例: `wp-custom-part` → `booking-reserve`）。
参照元の `wp:template-part` の `slug` も同時に変わること（`theme` 属性は移植先のテーマ名にする）。
**FR-2.4** 移植先のテーマを差し替えない。**有効なテーマのまま**、パッケージの項目だけを取り込めること
（現状は `get_stylesheet_directory()` のマニフェストを読むため、パッケージのテーマを有効化する必要がある）。
パッケージは ZIP アップロードで受け取り、一時領域に展開する。

### FR-3 エディター内パイプライン

**FR-3.1** 実行場所: 管理画面の専用ページ（ブロックエディターのスクリプトとブロック登録を読み込む）。
**FR-3.2** 各項目について §4 の流れで処理する。
**FR-3.3** 登録されていないブロックを含む項目は、変換を行わず、「未登録ブロック」として報告する。
**FR-3.4** 1項目の失敗が他の項目に影響しないこと。失敗した項目だけを報告し、他は続行できる。
**FR-3.5** 大きな本文（目安: 400KB、約70ブロック）を、画面が固まることなく処理すること（項目ごとに処理を分割して進捗を出す）。
**FR-3.6** 同じ項目を再実行しても、重複して作らない（既存の管理対象識別メタを継続して使う）。

### FR-4 変換規則（写像エンジン）

**FR-4.1** 規則は JSON で表す。1つの規則は「どのブロックの、どの属性パス」を「どう書き換えるか」を持つ。

```json
{
  "id": "color-slug-map",
  "match": { "attributePath": ["backgroundColor", "textColor", "borderColor"] },
  "map": { "content-back": "surface", "background": "base", "white": "on-image" }
}
```

```json
{
  "id": "value-map",
  "match": { "anyString": true },
  "pattern": "var(--wp--preset--spacing--(30|40))",
  "replace": "var(--wp--preset--spacing--20)"
}
```

**FR-4.2** 規則の種類（最低限）:

| 種類 | 対象 | 例 |
|---|---|---|
| スロット写像 | コアの色・フォントのスロット名（`backgroundColor` など。付随する `has-*` クラスは再生成されるので扱わない） | `content-back` → `surface` |
| 値の写像 | 属性値の中の文字列（正規表現可）。ネストしたオブジェクトも再帰的に | `Noto Sans JP, sans-serif` → `var(--wp--preset--font-family--gothic)` |
| 数値・単位の写像 | 幅、余白など | `width_val: wideSize` → `full` |
| 固定値の設定 | 属性を既定値へ戻す、空にする | `resourceId` → 既定値 |
| 属性の削除 | 属性を持たせない | |

**FR-4.3** 規則は**ブロック名で絞れる**こと。同じ属性名でも意味がブロックで違うため
（例: `selectedSlug` は、`design-button` では固定ページの slug、query-blocks では投稿タイプ）。
**FR-4.4** 写像表の UI を持つ。移植元で使われているスロット名・値を自動で列挙し、移植先の候補から選ばせる。
移植先に同名がある場合は既定で「そのまま」とし、無い場合は未設定として警告する（無言で効かなくならないようにする）。
**FR-4.5** 規則の組を**名前を付けて保存**できる（有効テーマごと、およびエクスポートして共有）。
**FR-4.6** 規則の適用結果は**差分**で見られる（変更された属性のパスと前後の値）。
**FR-4.7** 既定の規則セットを同梱する（kiln-theme 向け: 色スロット、フォント、余白 30/40→20・50→30、`wideSize`→`full`）。

### FR-5 サイト固有値の検出と除去

**FR-5.1** 変換の前に本文を走査し、次を一覧にする（場所、値、推奨の処置）。

| 種類 | 検出 | 既定の処置 |
|---|---|---|
| メールアドレス | `@` を含む文字列 | 空にする（`master_mail`・`master_name` など）。フッター文中は `[master_name]`/`[master_mail]` に置換 |
| メディア | `wp-content/uploads/` を含む URL、`core/image` の `id`、`design-button` の `media` | 空のブロックにする。`wp-content/plugins/` のアセットは、ホスト名だけ落としてルート相対にする |
| ID 参照 | 投稿 ID（`resourceId`、`wp:block` の `ref` など） | 既定値に戻す／パーツ参照に置換 |
| 絶対 URL | 移植元のホームURL、`.local` | `[home_url]` に置換 |
| 保存済みプレビューの文字 | 動的に置き換わるタイトルの見本（`resource_name` の `headingContent` など） | 空にする |
| 色の直書き | 16進数・`rgb()` | 報告のみ（変換するかは写像規則に委ねる） |

**FR-5.2** 検出ルールは、マニフェストの `siteSpecific` と、ブロック提供プラグインのフィルター
（既存の `itmar_btm_prepare_blocks` の後継）から拡張できる。
**FR-5.3** 処置は項目ごとに変えられる（除去／置換／そのまま）。「そのまま」にしたものは、レポートに残る。

### FR-6 リンクと参照

**FR-6.1** 内部リンクの対応表（移植元ページ → 移植先ページ）を作り、リンク属性を属性レベルで置換する。
**FR-6.2** 置換の対象キーは**ブロック名ごとに定義**する。固定ページを指すか、投稿タイプを指すかを区別する
（現状の既知の不具合: `selectedSlug` を無条件にページ slug へ書き換えて、`pickup-posts` の投稿タイプが壊れる）。
**FR-6.3** 同期パターン参照（`wp:block {"ref":…}`）は、移植先で採番された ID に置換する、またはパーツ参照に変換する（現状の機能を継続）。
**FR-6.4** 外部サイトへのリンクは変更しない。対応表に無いリンクは、レポートの「未解決」に載せる。

### FR-7 検証

**FR-7.1** 変換後の全ブロックで `isValid` を確認する。無効なブロックは、名前、ブロックのパス、
`validationIssues`（期待値と実際の値）を報告する。
**FR-7.2** 無効が1つでもある項目は、適用しない（P4）。ユーザーが明示すれば、その項目をスキップできる。
**FR-7.3** 安定性の確認: 書き出した本文を再度 `parse` し、全ブロックが有効で、再度 `serialize` した結果が一致すること。
**FR-7.4** 単体で実行できる検証モード（取り込みなしで、既存のパーツ・テンプレートの有効性を数える）を持つ。
開発サイトで、リリース前の確認にも使う。

### FR-8 焼き直し（bake）

**FR-8.1** 環境依存の値（影、ラベル幅など）を、移植先で計算し直すため、ブロックを**実際にマウント**する
（`BlockEditorProvider` ＋ `BlockList`）。
**FR-8.2** マウントは、画面外ではなく**見える状態**で行う。非表示のパネルでは、エディターの遅延更新が走らず、
計算結果が保存に反映されない（過去の実績）。進捗を出す専用のパネルを使う。
**FR-8.3** 焼き直し後の本文を、保存前に FR-7.3 の安定性確認にかける。
**FR-8.4** 焼き直しの前後で、環境依存でない属性が変わっていないこと（差分が、影・ラベル幅など定義済みのキーに限られること）を確認する。

### FR-9 保存と元に戻す

**FR-9.1** 保存先: 既定は、移植先データベースの `wp_template` / `wp_template_part` / `wp_block`（現状どおり）。
**FR-9.2** 適用前に、上書きされる既存の本文を**退避**する（リビジョンとは別に、取り込みごとに1世代）。
**FR-9.3** 取り込み単位で、一括の取り消し（退避した内容への復元）ができる。
**FR-9.4** 管理対象の一覧と、テーマ原本へ戻す機能（現状のゴミ箱への移動）を継続する。
**FR-9.5** 書き出す本文のエンコーディング・改行は、WordPress が保存する形式と一致させる（エディターの `serialize` の出力をそのまま保存する）。

### FR-10 依存の検査

**FR-10.1** 取り込みの前に、`requires` を検査する: プラグインの有効化、ブロックの登録、最低バージョン、投稿タイプの存在、オプション。
**FR-10.2** 不足があれば、何が足りないかを示す。自動の導入・有効化はしない。
**FR-10.3** `pages` がある場合は、ページの作成とテンプレートの割り当てを提案する（確認後に実行）。

### FR-11 ドライラン・レポート・ログ

**FR-11.1** 既定は**ドライラン**。「適用」を押すまで、データベースに何も書かない。
**FR-11.2** レポート（取り込みごと）: 項目ごとの結果、変換された属性の数、無効の一覧、サイト固有値の処置、未解決のリンク、未登録のブロック。
**FR-11.3** レポートは画面で見られ、JSON でダウンロードできる。
**FR-11.4** 取り込みの履歴を保持する（日時、パッケージ、実行者、結果）。

## 7. 非機能要件

| # | 要件 |
|---|---|
| NF-1 | 対応: WordPress 6.6 以上、PHP 8.1 以上（現行の 6.4 から引き上げる場合は、合意を取る） |
| NF-2 | 権限: `edit_theme_options`（現状に合わせる）。すべての書き込みは nonce 付きの REST で行う |
| NF-3 | 書き込み専用の公開エンドポイントを作らない（過去に一時の受け口を使ったが、作業後に必ず削除した）。保存は WordPress 標準の REST（`wp/v2/templates` など）を使う |
| NF-4 | 冪等性: 同じパッケージ・同じ規則で再実行すると、同じ結果になる |
| NF-5 | 性能: 70ブロック（約400KB）の項目を、1項目あたり数十秒以内で処理する |
| NF-6 | 国際化: 画面の文言は翻訳可能にする（日本語を同梱） |
| NF-7 | テスト: 変換・検証の中核を、エディター抜きで実行できる単体テスト（Node）と、実エディターでの統合テスト（ヘッドレスブラウザ）に分ける |
| NF-8 | ログ: 失敗の原因を、利用者が読める形で出す（「無効」だけでなく、期待値と実際の値） |

## 8. 画面（案）

「ツール → Theme Migration」に、次のステップを持つウィザードを置く。

1. **パッケージ**: ZIP を選ぶ／有効テーマ内のマニフェストを使う。依存の検査結果を表示
2. **項目の選択**: テンプレート・パーツ・パターンの個別選択。依存は連動。slug の付け替え
3. **写像**: 色・フォント・余白・幅の写像表。規則セットの読み込み・保存
4. **サイト固有値**: スキャン結果と処置の選択
5. **プレビュー（ドライラン）**: 項目ごとの結果、差分、無効の一覧。無効があれば適用不可
6. **適用**: 焼き直しの進捗、保存
7. **レポート**: 結果、未解決のリンク、設定の案内（作るべきページ、設定すべきオプション）

既存の「Distribution Export」タブ、管理対象の一覧は残す。

## 9. 技術設計メモ

### 9.1 実行基盤

- 管理画面の専用ページで、`wp_enqueue_block_editor_assets` 相当を読み込み、ブロックを登録した状態にする
- 解析・変換・検証は、`@wordpress/blocks` の `parse` / `createBlock` / `serialize` / `getBlockType` で行う（マウント不要）
- 焼き直しだけ、`@wordpress/block-editor` の `BlockEditorProvider` ＋ `BlockList` でマウントする
- 保存は `@wordpress/core-data` の `saveEntityRecord`（`wp_template` / `wp_template_part`）を使う

### 9.2 サーバー側（PHP）の役割

- パッケージの受け取りと一時展開、マニフェストの検証
- 依存（プラグイン、投稿タイプ、オプション）の事実の提供
- 移植先のページ、スロット（色・フォント・余白）の一覧の提供
- 管理対象の識別メタの管理、退避の保持
- ブロック本文の書き換えは**しない**

### 9.3 属性の走査

- 属性はネストしたオブジェクトのため、パス（`default_val.width_val` など）で再帰的に走査する
- 文字列に対する置換は、**属性値の文字列に限る**。本文全体には当てない
- 属性の更新は `createBlock(name, newAttributes, innerBlocks)` で作り直す。これにより、既定値の補完と整合が `save()` で自動的に取れる
  （過去の知見: 「復旧を試みる」と同じ処理）

### 9.4 注意が要る点（過去の実績から）

- 一部のブロックは、マウント時に既定値の無い属性（`shadow_result` など）を後から追加し、`data-attributes` の末尾に付く。
  定義順で再生成した文字列と一致せず、開き直しで無効になる既存の不具合がある。
  → 焼き直しの前に、各ブロックを属性から作り直す（FR-3 の流れ）。ブロック側の根本対応は別課題
- 浮動小数点: PHP の `serialize_precision` により、サーバーが返す raw が `0.69999999999999996` になる。
  比較は正規化して行う（FR-7.3）
- 環境により `DB_HOST` が `localhost` のままで CLI から接続できないことがあるが、本機能はブラウザ内で動くので影響しない

## 11. 受け入れ基準

**AC-1（実例）** 2026-10-04 に手作業で移植した予約管理ページ（時間あり・日単位）の2パーツを、同じ規則で再現できる。
- 全ブロックが有効（0件無効）
- サイト固有値（メール、リソース、ページ ID、見本の文字）が残らない
- 開き直しても内容が変わらない（浮動小数点の表記を除く）
- 手作業のときに必要だった、文字列置換・ファイルの手編集・一時の受け口が、いずれも不要

**AC-2（回帰）** 既存の移植（作品アーカイブ、ログイン、会員登録）が、新方式でも同じ結果になる（差分が、環境依存の値に限られる）。
**AC-3（失敗の扱い）** 未登録のブロック、無効なブロックを含む項目は、適用されず、原因が報告される。他の項目は続行できる。
**AC-4（取り消し）** 適用した取り込みを、一括で元に戻せる。
**AC-5（依存）** 必要なプラグイン・投稿タイプが無いとき、取り込み前に不足が示される。
**AC-6（単体テスト）** 変換規則（§6.4）の各種類に、エディター抜きで実行できるテストがある。
**AC-7（性能）** 70ブロック（約400KB）の項目を、検証まで含めて60秒以内に処理する。

## 14. 付録：実際の移植で使った処理（参考）

2026-10-04 に、予約管理ページの移植で、文字列処理で行ったこと。新方式では、①〜⑤が属性の変換規則になり、⑥⑦はエディターが自動で行う。

1. ヘッダー等のテンプレートパーツ参照の除去
