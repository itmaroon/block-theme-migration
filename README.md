# BLOCK THEME MIGRATION

WordPress標準のブロックテーマエクスポートを基礎に、開発環境での配布ZIP作成と、移植先サイトでのテンプレート割り当てを明確に分離するプラグインです。

## 使う順番

移植元（開発サイト）で書き出し、移植先で流し込む。**テーマは、移植先で先に導入しておく**（名前は、移植先で決めてよい）。このプラグインは、そのテーマの中身を整え、移植先のサイトに合わせるだけで、テーマの導入、プラグインの導入は行わない。

**移植元（開発サイト）**

1. 「Inspection」で、書き出す内容を確かめる。サイト固有の値、書き出しで外すもの、必要なプラグインとブロック、使っている投稿タイプ・タクソノミー・フィールドが出る。「Check that all blocks are valid」で、無効なブロックが無いことを確かめる。
2. 「Distribution Export」で、書き出さない項目があれば外して（Leave out）、書き出す。メール、移植元のメディア、内部リンク、ナビゲーションの参照、ID は、書き出しの時点で外れる。

**移植先**

3. 書き出した ZIP を、テーマとして導入して有効にする（「外観 → テーマ」。名前は、移植先で決めてよい。フォルダ名が配布時と違うと警告が出るが、そのまま進められる）。
4. 「Template Mapping」の上の「Requirements of this package」を見て、**足りないプラグインを導入して有効にする**。ERROR（足りない）を無くす。WARN（投稿タイプなど）は、次の紐づけで扱う。
5. 同じ画面の「Editable pattern import」で、同期パターンを取り込む。先にプレビューで確認する。
6. 「Binding」で、投稿タイプ・タクソノミー・カスタムフィールドを、**移植先にあるものに紐づける**。何も作らない。対応が無いものは「参照を外す」を選ぶ。
   - 「Preview」で、何がどう変わるかを確認する。
   - 「Apply bindings」で適用する。間違えたら、同じ画面の「Undo」で元に戻せる。
   - 2つ以上のテンプレート（またはパーツ）が、同じ名前に変わるときは（例: works と concept を、どちらも「投稿」に紐づけた）、**最初の1件だけ**を適用し、あとのものは「conflict」にして、そのまま残す（先のものを黙って上書きしない）。両方を使うときは、どちらかを別のものに紐づける。
   - **サブディレクトリにある WordPress（例: `https://example.com/sazanka/`）では、プラグイン・テーマ同梱の画像などのアドレスを、この移植先に合わせる。** 書き出しは、`/wp-content/plugins/…` のように、サイトの一番上を基準にした形で残すので、そのままだと、サイトの外を指して 404 になる。Binding の適用が、`/sazanka/wp-content/plugins/…` に直す（プレビューには、「asset-url」の変更として出る。Undo で戻せる）。サイトの一番上にある WordPress では、何もしない。
7. 「Inspection」の「Check that all blocks are valid」で、無効なブロックが無いことを確かめる。
8. 移植先のサイトエディターで、**外れたものを設定する**。画像、メニュー、ボタンやタイトルのリンク先、メール送信先（フォーム送信ブロックの管理者メール）が対象。

**覚えておくこと**

- 移植先の投稿・固定ページ・メディア・メニュー・表示設定には、書き込まない。
- 同期パターンの取り込みには、元に戻す機能が無い。やり直すときは、取り込んだパターンを管理画面で削除する。
- 紐づけは、テンプレート・パーツ・取り込んだ同期パターンに効く。テーマの `patterns/*.php` と、利用者が自分で作ったパターンは、書き換えない（Binding の画面に、該当があれば出る）。
- 実サイトに適用する前は、バックアップを取る。検証は、データベースとファイルを複製した検証用サイトで行う。

## 開発環境：Distribution Export

管理画面の「ツール → Theme Migration」を開き、「Distribution Export」タブを使用します。

- WordPressコアの `wp_generate_block_templates_export_file()` を使用
- テンプレートパーツのタイトルと領域を `theme.json.templateParts` に追加
- テンプレート内の同期パターン参照 `core/block` をテーマパターンへ変換
- 日本語の同期パターン名は `synced-pattern-{ID}` 形式のASCIIファイル名へ変換
- 開発サイトにある全 `wp_block` を、本文・同期状態・カテゴリー付きで `editablePatterns` に保存
- テンプレート表示を支える `patterns/*.php` は `Inserter: no` とし、ロックされた補助パターンを挿入一覧に表示しない
- 移植先で割り当て可能にするテンプレートと、1つの割り当て種別をラジオボタンで選択
- `front-page`、`404`、`index` などWordPressの階層で自動適用されるテンプレートは割り当て対象にできない
- `block-theme-migration.json` に `assignableTemplates` と検査結果を保存
- 開発サイトのホームURLをマニフェストへ保存（参照用。内部リンクは、書き出しの除去で外す）
- ローカル開発URLや未解決パターン参照を検査
- ダウンロード名を `{テーマスラッグ}.zip` にして、インストール後のテーマフォルダ名を開発時と一致させる

選択しなかったテンプレートもテーマZIPには含まれますが、移植先の割り当て画面には表示されません。

## 移植先サイト：Template Mapping

Distribution Exportで作成したテーマをインストール・有効化し、管理画面の「ツール → Theme Migration」を開いて「Template Mapping」タブを使用します。

- **同じ宛先に、2つ以上のテンプレートを割り当てない。** 割り当ては、宛先のテンプレート（たとえば `single-works`）を、データベースに作る。2つ以上が同じ宛先に割り当てられていると、最初の1件だけを適用し、あとのものは、理由を出して、適用しない（宛先と同じ名前のものが先）。たとえば、作業動画（`single-work-video`）を、作品の宛先に割り当てると、作品のテンプレートが、作業動画の中身に置き換わってしまう。
- **固定ページへの割り当ては、コピーを作らず、ページのテンプレートの指定を、テーマのテンプレートに、直接、設定する。** テーマの `theme.json` の `customTemplates` に、固定ページ用として登録されたテンプレート（`page-contact` など）が対象。ページ編集画面の「テンプレート」で、そのテンプレートを選ぶのと、同じ結果になる。コピー（データベース）を作らないので、テーマを更新（ZIP を入れ直す）すれば、そのまま反映される（古いコピーが、優先されて、古いままになることがない）。`customTemplates` にないテンプレートは、これまでどおり、ページの名前のコピー（`page-◯◯`）を作る。以前の版で作ったコピーは、ページが、テーマのテンプレートを指す間は、使われない。一番下の一覧で、ゴミ箱に移す。
- 割り当てたものは、画面の一番下の「Theme Migration-created theme content」に出る。そこで選んで、ゴミ箱に移すと、テーマのファイルの版に戻る。

- 有効テーマ内の `block-theme-migration.json` を読み込む
- マニフェストで許可されたテンプレートだけを表示
- 「Editable pattern import」で同期・非同期パターンを移植先の `wp_block` として作成または更新
- パターン内の同期参照を移植先で採番された投稿IDへ変換
- テーマテンプレート内の補助テーマパターン参照を、編集可能な同期パターン参照へ接続
- 移行元識別メタデータにより、再実行しても同じパターンを重複作成しない
- テーマフォルダ名が配布時と異なる場合も警告を表示して、現在の有効テーマ名でマッピングを継続
- マニフェストが更新されたときはWordPressのテーマパターンキャッシュを削除
- 移植先サイトに実在する固定ページを選択肢として取得
- 移植先サイトに実在する公開CPTとアーカイブ設定を選択肢として取得
- テンプレートと保存HTMLの再シリアライズ時はJSONの浮動小数点精度を安定化し、`0.7` が長い近似値へ変形してブロック検証エラーになることを防止
- JSONのオブジェクトと配列を区別して処理し、`displayMapping: {}` などの空オブジェクトが `[]` へ変形することを防止
- 旧 `design-calender` で動的デフォルトのためコメントから省略された `dateSpan` と `selectedMonth` を保存HTMLから復元し、月替わりの検証エラーを防止
- 生成した `wp_template` に移行元・割り当て先・テーマを記録し、同一マッピングの再実行では重複作成せず更新
- パターン再接続によるテンプレートとテンプレートパーツも管理対象として識別
- 移行ツールが管理するテンプレートとテンプレートパーツだけを一覧表示し、個別または一括でゴミ箱へ移してテーマ原本へ戻せる
- 移植先に合わせたテンプレート名を保存し、移行元と移行先の同名表示を避ける
- プレビュー後に適用
- マッピングの選択状態を有効テーマごとに期限なしで保存し、再プレビューや画面再訪問後も復元
- マッピング元と移行先のslugが異なる場合、チェックした旧 `templates/{source}.html` を次回のDistribution Export ZIPから除外
- 旧テンプレートの除外時は、対応する `theme.json.customTemplates` 定義とマニフェスト項目も同時に整理（有効テーマの実ファイルは変更しない）
- ブロック固有の旧属性補正は `itmar_btm_prepare_blocks` フィルターでブロック提供プラグインへ委譲

割り当ては移植先データベースへテーマ固有の `wp_template` として保存し、テーマファイル自体は変更しません。

マッピング後に整理済みテーマを作る場合は、不要になったマッピング元ファイルの削除欄をチェックして設定を保存してから、Distribution Exportを実行します。マッピング先のデータベーステンプレートはWordPress標準エクスポートによって新しいslugのHTMLファイルになり、チェックした旧ファイルだけがZIPから除外されます。

移植先では先に「Editable pattern import」を実行し、その後にテンプレートマッピングを実行します。非同期パターンは編集可能なマイパターンとして復元されますが、開発サイトですでに通常ブロックへ展開されている既存箇所をパターン参照へ戻すことはしません。

マニフェストがないテーマでは割り当て画面を使用できません。テーマフォルダ名がマニフェストと一致しない場合は警告を表示しますが、現在の有効テーマを対象として割り当てできます。

## 点検：Inspection（0.6 で追加）

管理画面の「ツール → Theme Migration」の「Inspection」タブ。**読み取り専用**で、書き出しの前に、テーマの状態を確認します。
要件は `docs/requirements-v0.2.md`、調査結果は `docs/link-attribute-survey.md`。

- **書き出しに何が入るか**: `style.css`、`theme.json`（version）、スクリーンショット、`styles/`（バリエーション）、`patterns/`、重いファイル
- **棚卸し**: テンプレート・パーツ・テーマのパターン・同期パターンを、次の観点で一覧
  - DB が、テーマファイルを上書きしているか（DB だけのものもあるか）
  - どこからも使われていないパーツ・パターン（挿入できるパターンは、サンプルとして扱う）
  - 参照が途切れていないか
  - テンプレートが、どの経路で表示されるか（自動、`customTemplates`、`page-{slug}` のページの有無、投稿タイプ・タクソノミーの有無）
  - このサイトの投稿タイプ・タクソノミーに、専用のテンプレートが無いもの（汎用のテンプレートで表示される。情報として表示）
- **サイト固有値のスキャン（検出のみ。書き換えない）**: 内部リンク、外部リンク（残す）、ナビゲーションの参照、メディア、メールアドレス、`.local` の URL、保存された投稿データ、予約のリソース、
  投稿タイプ・タクソノミー・カスタムフィールドの参照（紐づけの対象）。規則は `includes/link-rules.json`
  （ブロック名ごと。`linkKind` の条件、埋め込まれたブロックの再帰に対応）。ブロックを提供するプラグインは、フィルター `itmar_btm_block_rules` で規則を追加できる
- **ブロックの有効性の検査**: ブラウザー内で、全項目をエディター自身の検証にかけ、無効なブロックと原因を表示（処理中は表示を出す）
- 結果は JSON でダウンロードできます（`assets/inspect.js`、REST `itmar-btm/v1/items`・`itmar-btm/v1/report`。ともに読み取り専用）

## デモ用の書き出し（Demo export）

Distribution Export の画面にある「Demo export」にチェックを入れて書き出すと、**デモサイト（WordPress Playground など）用**の ZIP になる。ファイル名は `{テーマ}-demo.zip`。**配布には使わない。**

- ページへのリンク、アップロードしたメディアを、**残す**。サイトのアドレス（`https://…`）だけを外して、相対にする（`https://sazanka.local/booking/` → `/booking/`、ホームそのものは `/`）。同じスラッグのページを、デモの中に作れば、リンクがつながる。メディアは、同じパスにファイルを置けば、表示される。
- 投稿・メディアの ID と、予約のリソースなどの参照も、**残す**（デモは、同じ ID で見本の中身を作る）。
- メールアドレス、ナビゲーションの参照、外部サービスの設定は、通常の書き出しと同じく、外す。
- manifest に `"demo": true` が入る。
- `tests/m4-sanitizer-smoke.php` が、デモ用の変換（リンク・メディアが残り、相対になる、冪等）を確かめる。sazanka（kiln-theme）で書き出すと 0.38MB で、ブロックは 54項目・951ブロック、無効 0。

## 書き出しから項目を外す（0.6 で追加）

Distribution Export で、テンプレートとテンプレートパーツに「Leave out」のチェックを追加しました。外した項目は ZIP に入らず、`theme.json`（`customTemplates`・`templateParts`）と
マニフェスト（`excluded` に記録）からも消えます。外さない項目が参照しているパーツは、外せません（理由を表示して中止）。

## 動作要件

WordPress 6.6 以上（出力が `theme.json` version 3 のテーマになるため）、PHP 8.1 以上。

## データモデルと依存の宣言（0.6 で追加）— マニフェスト v5

Distribution Export が作るマニフェスト（`block-theme-migration.json`）が、`schemaVersion: 5` になり、次を持ちます（v4 のキーは、そのまま残る。v2〜v5 を読める）。

- **`requires`**: 必要な WordPress の最低バージョン（6.6）、必要なプラグイン（フォルダ名、名前、バージョン、提供するブロック、理由）、使われているブロックの一覧。
  プラグインは、ブロックを提供しているスクリプトの場所から判定し、プラグイン自身が宣言している依存（`Requires Plugins`）も足す。カスタムフィールドの参照があるときは、SCF／ACF を「任意」の依存として足す。
- **`dataModel`**: 投稿タイプ（ラベル、アーカイブの有無、REST の基底名、サポート、タクソノミー）、タクソノミー、フィールドグループ（SCF／ACF から**読み取り専用**で取得。フィールド名・種類・選択肢、対象の投稿タイプ）、
  投稿メタ（`meta_` で始まる参照。登録されたメタキーか）、使用箇所の索引（どのテンプレート・ブロック・属性が、何を参照しているか）。
  **情報として書き出すだけで、移植先で作ることはしない。** 移植先に既にあるものに紐づけるための手がかり。
- 書き出しから外した項目（「Leave out」）は、宣言の対象からも外れる。

移植先の「Template Mapping」タブの上に、**依存の検査**のパネルが出ます（v5 のパッケージのみ）。WordPress のバージョン、プラグイン（未導入・無効・古い）、ブロックの登録、投稿タイプ・タクソノミー・投稿メタ・カスタムフィールドの有無を、OK／要確認／不足で表示します。
不足は示すだけで、自動の導入・有効化・作成はしません。「Inspection」タブにも、書き出し前に同じ内容（宣言）が出ます。

## 紐づけ：Binding（0.6 で追加）

移植先に既にある投稿タイプ・タクソノミー・カスタムフィールド（SCF／ACF）へ、テーマの参照を付け替える。**何も作らない。**

- 画面（Binding タブ）に、有効なテーマのテンプレート・パーツが参照しているものを並べ、移植先の候補から選ぶ。初期値は、同名があれば「そのまま」、無ければ名前・ラベルが近いもの、それも無ければ「参照を外す」。
- **プレビュー**は何も保存しない。何が・どう変わるかを、ブロックごとの差分で見せる。
- **適用**は、データベースのテンプレート・パーツ（ユーザーのカスタマイズ層）に保存する。テーマのファイルは変えない。`archive-◯◯` `single-◯◯` `taxonomy-◯◯` は、紐づけ先の名前で保存する（同名のテンプレートが既にあれば、上書きを許可するまで触らない）。
- 適用のたびに元の状態を記録する。**元に戻す**と、作ったものはゴミ箱へ、更新したものは元の本文へ戻る。
- 書き換える属性は、ブロックごとの規則（`includes/link-rules.json`）で決まる。ブロックコメント・`data-attributes`・属性ごとの `data-*`（`data-selected_slug` など）を対で直す（食い違うとエディターで「ブロックが無効」になる）。
- `choiceTerms`（移植元のターム ID）は、必ず空にする。
- 「Editable pattern import」で取り込んだ同期パターン（`wp_block`。取り込み元の識別メタが印）も、テンプレートと同じく、計画・適用・元に戻すの対象にする。利用者が自分で作ったパターンは書き換えない。
- テーマのパターン（PHP）と、取り込んだものではない同期パターンは、自動では書き換えない。該当があれば、画面に挙げる。

テスト: `tests/m3-binder-smoke.php`（変換）、`tests/m3-binding-apply-smoke.php`（計画・適用・元に戻す）。

## 書き出し時の除去（0.6 で追加）

Distribution Export は、書き出す前に、テンプレート・パーツ・変換した同期パターンから、移植元のサイト固有のものを外す（`includes/class-sanitizer.php`）。

| 対象 | 処置 |
|---|---|
| 内部リンク（`selectedPageUrl`、固定ページの `selectedSlug`、本文中の `<a href>`） | 空にする（本文中は `#`）。外部リンクは残す |
| ナビゲーションの参照（`core/navigation` の `ref`） | 外す |
| メールアドレス | `[master_mail]`（属性・タグ・文のどこでも同じ。保存内容の整合のため） |
| 移植元のアップロード（`wp-content/uploads`） | `core/image` は画像だけ外して器を残す。ブロックの画像属性は既定値に戻す |
| 投稿 ID・リソース ID・外部サービスの設定値 | 既定値に戻す |
| プラグイン・テーマ同梱のアセットの URL | 移植元のホストを外し、ルート相対にして残す |

- 属性は、`includes/link-rules.json` のブロックごとの規則で決まる。規則の `html` は、属性の変更に合わせて直す保存済み HTML の場所（`attr:data-…`、`remove:figure`、`removeattr:href`）。
- 何を外したかは、manifest の `removals`（種類ごとの件数と、外した内部リンクの一覧）に入る。メールアドレスそのものは記録しない。
- Inspection タブに、書き出しで外す件数が出る。
- **属性の書き足し**（除去ではない）: 初期値がサイトの言語で変わる属性（フォーム系の `stage_info`・メールの件名と本文、`design-select` の `folder_val`、`design-text-ctrl` の `placeFolder`）は、初期値と同じ値だとブロックコメントから省かれ、HTML の `data-attributes` にだけ移植元の言語の文言が残る。移植先の言語が違うと、初期値が変わって保存内容と食い違い、ブロックが無効になる。書き出しのときに、その値をブロックコメントに書き足して、どの言語のサイトでも一致させる（`Itmar_BTM_Sanitizer::LOCALIZED_DEFAULTS`）。
- **Font Library のフォントを、テーマに入れる**（除去ではない）: サイトエディターの Font Library で入れたフォントは、データベースと `uploads/fonts` にあり、書き出される `theme.json` の `fontFace` の `src` が、移植元のアドレス（`https://…/uploads/fonts/…`）のままだと、移植先で読めない。書き出しのとき、そのファイルを、ZIP の `assets/fonts/<スラッグ>/` へコピーし、`src` を `file:./assets/fonts/…` に書き換える（`localize_font_files`）。すでにテーマに同じ内容のファイルがあれば、それを指す（同じファイルを 2 度入れない）。外部のアドレスや、見つからないファイルは、そのまま残して、manifest の `fonts.skipped` に挙げる。入れたものは、`fonts.localized` に挙げる。
- フォントを入れたあと、サイトのユーザーのスタイルに、テーマのフォント一覧の古い写し（`fontFamilies.theme`）が残っていると、`theme.json` に足したフォントが、そのサイトでは、見えない（移植先の新しいサイトでは、起きない）。
- **翻訳されたラベルを英語に戻す**（`normalize_saved_labels`）: design-radio の「Clear」、design-select の選択肢の先頭の「Please Select.」、design-text-ctrl の「Address Search」と郵便番号の例、code-highlight の「Copy」は、昔の `save()` が、サイトの言語で訳して保存していた。書き出しのとき、移植元の言語で訳された文言を、英語に戻す（訳は、移植元サイトの翻訳ファイルで引く）。block-collections 2.3.0 以降は、`save()` が英語で保存し、表示のときにサーバー側で訳す。2.3.0 より前のブロックでは、移植先で無効に見えるので、移植先に、2.3.0 以上を入れる（Requirements に、最小の版が出る）。
- 数値・金額の表示形式（design-title）も、2.3.0 から、サイトの言語に左右されない形（金額は日本円）で保存する。昔の保存内容は、ブロックの `deprecated` が読む。
- 残るもの: 日付形式（design-title の日付タイプ。月名・曜日名がサイトの言語で変わる）。
- 書き出した ZIP にサイト固有のものが残らないこと（AC-2）は、`tests/m4-sanitizer-smoke.php` が、実際の書き出しで確かめる。ブロックの有効性は、除去後の内容を Inspection の検査にかけて確かめる（develope-equip で 1,127 ブロックすべて有効）。
- 変換した本文は、エディターの `save()` が出す形と一致していなければならない。PHP からは `save()` を実行できないので、新しいブロックを規則に足すときは、`save.tsx` が属性から出す HTML（`data-*`、`<img src>`、`<a href>` など）を確かめて、`html` を指定する。


## 子テーマと、ほかの書き出しプラグインとの違い

2026-10 に、Twenty Twenty-Five・Extendable・YITH Wonder（公開されているブロックテーマ）と、公式プラグイン「Create Block Theme」（以下 CBT、2.10.2）で、同じ条件で比べた結果。

### 子テーマとの関係

- 子テーマは、親テーマを更新しても、手元の変更を残すためのしくみ。Theme Migration は、別のサイトで動かすためのしくみで、解く問題が違う。組み合わせて使える。
- 子テーマが有効なとき、Distribution Export は、子テーマとして出る（`style.css` の `Template:` が残る）。ZIP に入るのは、テンプレート・パーツ（親のものも、子の分としてコピー）、`theme.json`（親の設定を統合したもの）、`style.css` だけ。パターン、スタイルのバリエーション、フォント、`functions.php` は、親に頼る。**この ZIP を入れる先には、親テーマが先に必要。**
- 今の制限: 親テーマの名前を、manifest に記録しておらず、「Requirements」にも出ない。親のテンプレートを子へコピーするので、親の更新は、そのコピーに届かない（CBT は、子で変えたものだけを出す）。

### Create Block Theme との違い

標準のテーマ（子テーマでない）では、データベースの変更（テンプレート・パーツ・グローバルスタイル）の書き出しは、ほぼ同じ（どちらも、WordPress 標準の書き出しが土台）。違いは、次のとおり。

| | Create Block Theme | Theme Migration |
|---|---|---|
| データベースの同期パターン・未同期パターン（`wp_block`） | **書き出さない。** テンプレートの `wp:block {"ref":ID}` は、移植元の ID のまま残り、移植先では、参照が切れる | テーマのパターンのファイルに変換（テンプレートの参照も `wp:pattern` に変換）。本文・同期状態は、`editablePatterns` に保存し、移植先の「Editable pattern import」で、`wp_block` として戻せる |
| サイト固有の値（移植元のアドレス、アップロード画像、メール、移植元のページへのリンク、画像の ID） | そのまま残る | 書き出しのときに外す |
| 言語で変わる保存内容 | そのまま。別の言語のサイトで、ブロックが無効になる | 書き出しのときに、そろえる（英語の移植先で、無効 0） |
| 必要なプラグイン・ブロック、投稿タイプ・タクソノミー・フィールドの宣言と検査 | なし | あり（manifest v5、Requirements） |
| 投稿タイプなどの紐づけ、ページへの割り当て | なし | あり（Binding、Template Mapping） |
| 子テーマの出力 | 子で変えたものだけ（小さい） | 親のテンプレート・パーツも、コピーして出す |

sazanka（kiln-theme、日本語）の複製から書き出し、英語の空のサイトに取り込んだ結果は、Theme Migration の ZIP が、無効なブロック 0、CBT の ZIP が 17（フォーム系ブロック、ラベル）。CBT の ZIP には、移植元のアドレス、アップロード画像の参照、メールアドレスも残った。

試していない範囲: CBT の「テーマに変更を保存」「テーマを複製」（画像をテーマの中へ取り込む機能）、画面（サイドバー）の操作。

## テスト

WordPress を読み込んで実行する（`tests/*.php`）。ブロックの有効性は、Inspection タブの検査（ブラウザー）で確かめる。

| テスト | 対象 |
|---|---|
| `inspector-smoke.php` | 点検（サイト固有値のスキャン、棚卸し） |
| `m2-datamodel-smoke.php` | データモデルと依存の宣言、依存の検査、manifest v5 |

| `m3-asset-prefix-check.php` | 移植先のアドレスに合わせる処理（サブディレクトリのサイト） |
| `m3-mapping-collision-check.php` | 割り当てで、同じ宛先に複数が割り当てられたときの扱い |
| `m3-mapping-direct-check.php` | 固定ページへの割り当て（テーマのテンプレートを、直接、指定。コピーを作らない） |
| `m4-sanitizer-smoke.php` | 書き出し時の除去（合成＋実際の書き出し） |
